# 当前评估与改进路线

初次评估：2026-09-22；实施进度更新：2026-09-23。下面的 P0/P1 表保留评估时的依据，当前交付范围以本节为准。

## 本轮已实施（2026-09-23）

- 启动：音频默认端口统一为 8767，启动脚本支持参数，缺少环境/端口占用时给出操作指引；终端和页面可检查配置、解码器、证书与运行版本。新版页面连接旧服务会直接提示重启。
- 诊断：页面及 `audio-doctor --network` 支持 DNS/TCP/TLS 检查，不发送 HTTP 请求，不调用付费生成。
- 恢复：任务展示当前步骤、最后已确认步骤、最近尝试及供应商任务 ID；已生成整曲的分轨/MIDI 未完成情况也进入任务动态。恢复操作不重新生成或分离。
- 试听：同位置 A/B 切换、循环范围、保存在 SQLite 的音轨时间点备注；备注可删除，作品打包时一并导出。
- 导出：按作品名打包当前本地原曲/分轨/MIDI、描述/歌词、试听备注与文件清单；缺失内容明确列出，不为打包补发任何网络请求。
- 维护：抽出前端通用、运行检查、任务与试听模块；无活跃任务时降低轮询频率，隐藏标签页暂停定时刷新；音频后台/历史扫描复用带文件状态约束的哈希校验，直接下载仍完整校验。
- 曲库：每页 30 首，任务动态独立每页 10 条；全库搜索/收藏/排序、跨页保留播放和 A/B，批量操作明确限定当前页。新增持久变化序号，轮询先检查变化，不再反复拉取全量历史。
- 验证：新增离线回归与 JavaScript 测试，补 6 条 Playwright 浏览器场景并配置 GitHub Actions。浏览器关键流程已在独立 Mock 库实测，完整无头 Chromium 套件已通过；远程 CI 待上传后验证，详见验收记录。

仍待后续：真实波形、更完整的前端状态拆分、浏览器回归的持续运行与更多场景、配置编辑页与人工音质评价。此次未改变付费传输重试策略，也未实现跨地址连接回退。

## 判断

BeatMate 已经能走通两条创作流程：描述生成伴奏，或歌词生成歌曲并分离音轨。试听、文件校验、下载、曲库管理以及任务恢复都有实现基础。现阶段最有价值的投入，是让第一次运行、故障恢复和反复试听变得稳定、易懂，而不是马上增加模型数量或复杂的 DAW 功能。

产品仍是个人本地 MVP。主要短板是启动与版本管理分散、故障后缺少集中的下一步指引、听感质量缺少可重复的评价，以及前端代码不利于继续迭代。

## P0：让第一次使用和恢复任务可靠

| 方向 | 当前证据 | 建议改动 | 验收目标 |
| --- | --- | --- | --- |
| 启动检查与版本提示 | 多次出现新静态页面连接旧 Python 服务；默认端口和启动脚本端口不同 | 统一入口，启动时检查端口占用、配置、数据库位置、解码器和服务版本；界面集中展示诊断结果 | 新用户按 README 可启动；旧进程占用时明确指出原因和处理办法 |
| 无扣费连接诊断 | 已区分 DNS/TCP/TLS，但需要从终端排查；当前只选解析后的一个地址连接 | 提供不提交生成的诊断；评估在 HTTP 发送前尝试其他已校验地址，并明确代理支持范围 | 可区分域名、端口、证书和服务配置问题；诊断不创建任务、不扣费、不弱化 TLS |
| 任务恢复中心 | 失败、结果不确定、分离下载失败含义不同；用户容易把临时查询失败当成整首生成失败 | 展示当前步骤、最后成功步骤、最近尝试时间、任务 ID 和下一步；保留查询/下载恢复与再生成的区别 | 用户能判断应该等待、恢复下载还是核对账户；不需要猜测是否重复收费 |
| 持续验证 | 有 Python 单元/接口测试和手工浏览器验收，尚无仓库 CI 或持续浏览器回归 | 先接入离线 CI，再覆盖预览、重复点击、刷新恢复、播放器切换和回收站等关键浏览器流程 | PR 自动验证离线流程；默认流水线不使用真实 Key 或付费生成 |

本地额度当前保守地计算预留次数，失败后不自动释放。若改进，应明确区分“已预留、已发送、未确定”，并迁移旧记录；不能把推测的未扣费直接作为可用余额。

## P1：提升试听效率与代码可维护性

| 方向 | 为什么值得做 | 建议范围 |
| --- | --- | --- |
| 比较版本与标记片段 | 核心判断发生在试听，不在表单里 | 同位置 A/B 切换、循环区间、时间点备注；从真实音频计算波形，不用装饰波形冒充分析 |
| 打包导出 | 进入 DAW 后还要整理文件 | 以作品名命名下载，打包原曲/分轨/MIDI及说明，附时长、格式与来源；不承诺生成完整 DAW 工程 |
| 分离与 MIDI 质量说明 | 用户已遇到纯伴奏残留人声、MIDI 听感差异 | 先建立人工评价和样本记录，区分音符转录与声音还原；标记缺失、串音、音符密度等具体问题 |
| 前端模块化 | 当前 `studio.js` 集中处理请求、状态、渲染、表单和播放，CSS 多次追加覆盖 | 拆成创作、曲库、播放器、任务和请求模块，统一设计变量与状态更新；优先保持原生技术栈，按需要再评估框架 |
| 曲库读取性能 | 页面每 3 秒取全量历史；历史读取会对音频文件做哈希核验 | 分页/增量更新任务，缓存有文件大小和时间信息约束的校验结果，保留下载及异常时的校验 | 
| 草稿和配置体验 | 草稿存在浏览器，本机配置来自 `.env` 与持久额度设置 | 展示明确保存状态和当前数据目录，增加草稿命名/恢复；设计安全的本机配置入口，不把 Key 返回浏览器 |

## P2：有需求和质量证据后再扩展

- 更多供应商：先稳定统一的任务/产物契约，再加适配器，避免把不同服务能力伪装成相同选项。
- BPM、调性和响度分析：标记为检测结果及置信度，与用户的请求参数分开。
- 更细分轨和 MIDI 编辑：以实际转录质量为依据，不能仅增加下载按钮就宣称可还原编曲。
- 原生 Windows、打包桌面应用或多用户云端：需要额外的锁、存储、鉴权与部署设计，当前不作为小改动承诺。

## GitHub 发布准备

当前目录尚无 Git 元数据。发布前建议完成以下事项，而不是直接上传整个工作目录：

- **说明当前产品。** README 已按产品、上手、配置、架构、边界重排；早期原生 MIDI 和 API 说明已拆分。
- **保留代码，排除本机数据。** `.env`、`.beatmate/`、`.venv/`、`output/` 等已忽略；首次暂存后仍应检查实际清单，尤其是报告、日志和截图。不要上传个人生成历史或含 Key 的终端截图。
- **项目许可证。** 已添加 MIT LICENSE，并在 README 区分代码许可、第三方依赖与生成音乐使用条件。
- **补独立的产品截图和演示。** 使用无个人信息的演示库，展示创作区、曲库、三轨和导出。现有封面可以表达风格，但不能代替使用演示；Mock 音频必须标为测试信号。
- **验证 CI。** 已加入离线及浏览器 CI 和贡献说明；上传后检查首轮 Actions 结果，失败时按 trace 排查。
- **区分历史与现状。** 设计和验收文档保留历史过程，首页以当前代码能力为准。不要把不同日期的局部测试或人工评估汇总成不存在的质量保证。
